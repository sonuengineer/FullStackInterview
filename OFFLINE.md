# Offline support

The dashboard works without a network. A hand-written service worker (`sw.js`)
caches the app shell on install and everything else as you open it.

No npm, no Workbox -- `sw.js` is plain JS and `tools/build-sw.mjs` is a plain Node
ESM script like the other `tools/build-*.mjs`.

## Files

| File | What it is |
|---|---|
| `sw.js` | The service worker. The constants between `/* SW-BUILD-START */` and `/* SW-BUILD-END */` are generated -- do not edit them by hand. |
| `manifest.webmanifest` | Web app manifest, so the site can be installed on Android. |
| `icons/icon.svg` | The app icon (full-bleed, `purpose: "any maskable"`). |
| `tools/build-sw.mjs` | Writes the generated block into `sw.js` and injects three marked blocks into `index.html`. |
| `index.html` | Holds the generated blocks `SW-HEAD`, `SW-TOAST` and `SW-REGISTER`. Nothing else was changed. |

## What is precached (on install, about 1.15 MB)

* `./` -- the dashboard itself. `/` and `/index.html` are the same 1.1 MB file, so
  only one copy is stored and both URLs are served from it.
* `manifest.webmanifest` and `icons/icon.svg`.
* `marked` from cdnjs -- without it nothing renders at all.

That is the whole install. Every lesson is already inlined in `index.html`, so this
one file is what makes the lessons readable offline.

## What is cached on demand (first time you open it)

Everything else: `systemdesign/**/*.md`, the three framed reading apps
(`ai-course/`, `ai-ebook/`, `ai-guide/` and their css/js), `Images/*`,
`systemdesginchectsheet/*` (PDF and HTML), `prep/index.html`, Google Fonts, and
highlight.js. **Anything you have opened once stays readable offline.** Anything
you never opened shows a small "you are offline" page (for a page) or the site's
own "Could not load this part" message (for a system design part).

`mermaid` (~2.8 MB) is deliberately **not** precached. The page loads it on every
online visit anyway, so the worker copies it from the browser's HTTP cache into the
runtime cache right after the page is up (the `WARM` message). Net effect: the site
is fully offline-ready after one online visit, without a 2.8 MB install.

## Strategy per asset class

| Asset | Strategy | Why |
|---|---|---|
| Top-level navigations, `index.html` | **Network-first**, cache fallback | `index.html` is the whole app and is rebuilt constantly. Cache-first here is how a static site becomes permanently un-updatable. |
| `systemdesign/**/*.md`, framed apps' html/css/js, manifest | Stale-while-revalidate | Instant from cache, refreshed in the background. Vercel sends an ETag, so the refresh is usually a 304. |
| Images, PDFs, fonts, icons | Cache-first | The bytes do not change; a revalidation would be wasted. |
| cdnjs, fonts.googleapis.com, fonts.gstatic.com | Cache-first | URL-versioned libraries. |
| Any other cross-origin host | Not touched | Only the hosts the site actually depends on are cached. |
| Byte-range requests (PDF viewer) | Network, cache fallback | `cache.put()` rejects a 206, so partial responses are never stored. |

## Versions and cleanup

Two separate versions, on purpose:

* `SHELL_VERSION` -- generated by `tools/build-sw.mjs` as a hash of the deployed
  `index.html` plus the precache list, so it only changes when something real
  changed. It names the shell cache `dash-shell-<hash>`.
* `RUNTIME_VERSION` -- a constant **bumped by hand** in `sw.js`, and only when the
  cache layout or a strategy changes. It names `dash-runtime-<n>`.

They are split because the runtime cache is the user's offline library -- possibly
many MB of parts, PDFs and diagrams they chose to save. Wiping that on every content
deploy would be the wrong trade. On `activate` the worker deletes every cache named
`dash-*` that is not one of the two current ones, and leaves other caches alone.

### Bumping a version

* Content change (new lesson, rebuilt `index.html`): just run
  `node tools/build-sw.mjs`. The shell hash changes by itself.
* Strategy or cache-layout change in `sw.js`: edit `RUNTIME_VERSION` by hand, then
  run `node tools/build-sw.mjs`.

## Build order

`tools/build-sw.mjs` must run **after** any script that rewrites `index.html`
(`build-lessons.mjs`, `build-systemdesign.mjs`, `build-cheatsheets.mjs`,
`build-aitrack.mjs`, `build-ai.mjs`, `build-networking.mjs`), so the hash matches
the file that is actually deployed:

```
node tools/build-lessons.mjs
node tools/build-systemdesign.mjs
...
node tools/build-sw.mjs        # last
```

Re-running it is a no-op: it injects into `index.html` first and hashes the result,
so a second run produces no diff.

## Update flow

A new `sw.js` installs in the background and waits. The page shows a small
"New version available / Reload" pill (bottom right, same card + accent style as the
toolbar). Clicking it posts `SKIP_WAITING` to the waiting worker and reloads once.
`skipWaiting()` is never called unprompted, so a reader is not swapped onto a new
build mid-page.

The first time the worker activates, a one-time note says that pages you open are
saved for offline reading. It is remembered in `localStorage` under
`dashboard.offlineNoteSeen`.

## Clearing a stuck cache during development

1. DevTools > **Application** > **Storage** > **Clear site data** (tick
   "Unregister service workers"), then hard-reload.
2. Or from the console:

```js
// what is stored
await caches.keys();
// nuke everything and start over
for (const k of await caches.keys()) await caches.delete(k);
for (const r of await navigator.serviceWorker.getRegistrations()) await r.unregister();
location.reload();
```

3. DevTools > Application > Service Workers > **Update on reload** while working on
   `sw.js`.

The worker is registered with `updateViaCache: 'none'`, so the browser always
revalidates `sw.js` itself against the network.

## Known limits

* **It does not run on `file://`.** Service workers need a secure context.
  Registration is guarded to `https:`, `localhost` and `127.0.0.1`, and the
  `<link rel="manifest">` is added by script for the same reason -- a static link
  tag would make Chrome log a CORS error on every local read. Opening
  `index.html` from disk behaves exactly as it always did.
* **The first visit is not fully covered.** The worker only starts controlling the
  page part-way through the first load, so assets requested before that (the CDN
  libraries in `<head>`) are picked up by the `WARM` message or on the next visit.
* **Offline PDFs are not guaranteed.** Chrome's PDF viewer uses byte-range
  requests, which cannot be stored in the Cache API. The first (non-range) request
  is cached, so a PDF may or may not open offline depending on how Chrome fetches
  it.
* **Opaque responses cannot be validated.** If a CDN ever answers a plain
  no-cors request with an error page, the worker cannot tell (`status === 0`). It
  asks for `cors` first, where a real status is visible, and only falls back to
  no-cors.
* **A slow network is not a fast failure.** Navigations are network-first with no
  timeout, so a truly offline reload is instant (the fetch rejects at once) but a
  very slow connection still waits for the network instead of serving the cache.
* **No background sync and no push.** Nothing is downloaded that you did not open.
* **Installability**: the manifest ships a single SVG icon. Current Chrome accepts
  SVG icons, but if an install prompt ever misbehaves, add PNG 192 and 512 files to
  `icons/` -- `tools/build-sw.mjs` picks up any `.png` or `.svg` there
  automatically, and the manifest's `icons` array is the only thing to extend.
