## 1. Today in one line

You let the agent work unsupervised on long tasks — which means today is really about the rails that make that survivable.

---

## 2. The problem

Your Day 7 agent works, but only while you are watching it.

`max_steps=8`. Every note save waits for you to type `y`. You read each step as it scrolls past. That is fine for a demo and useless for anything real.

A genuinely useful task looks like this:

> Go through all my documents, find every deadline mentioned, check which ones have already passed, and write me a summary note.

That is fifteen to twenty steps. You cannot sit and approve twenty actions — at that point you may as well do it yourself.

So turn the dials up: `max_steps=30`, remove the approval prompt. Now try it.

Three things go wrong, and all three will happen to you:

- **Your quota disappears.** Twenty steps, each re-sending everything, is tens of thousands of tokens.
- **It stops halfway and tells you it finished.** You get a confident summary, and the note is empty.
- **It gets stuck.** The same search, eight times, with slightly different wording, until the step limit kills it.

Autonomy is not a setting you switch on. It is a set of things you have to build *before* you can safely stop watching. That is today.

**One sentence to carry through the whole lesson:**

> The agent must never be the judge of whether it succeeded.

---

## 3. Mental model

**Think about the difference between a colleague you watch and a colleague you send off for the afternoon.**

To send someone off, you need five things:

1. **A clear goal** — so they know what finished looks like.
2. **Boundaries** — which systems they may touch, and which they may not.
3. **A budget** — do not spend three days on this.
4. **A report** — tell me what you actually did.
5. **A way to stop them** — if this goes wrong, it must be possible to end it.

Every one of those becomes code today.

**Where the comparison breaks, and this is the whole lesson:**

**A person tells you when they are stuck.** They come back and say "I couldn't find it, what do you want me to do?" An agent does not do this unless you build it. Left alone, it either loops silently or produces a confident report of work it never did.

**A person knows the difference between doing something and describing it.** The model does not. Writing "I have saved your summary to notes/deadlines.txt" costs it exactly the same effort as saving the file. Nothing in how it works distinguishes those two acts.

Which is why verification cannot be a matter of asking nicely in the prompt. It has to be a separate check, run outside the agent, on evidence rather than on claims.

---

## 4. How it really works

**Autonomy is a set of dials, not a switch.**

| Dial | Low | High |
|---|---|---|
| Step budget | 5 | 50 |
| Token budget | 5,000 | 200,000 |
| Time budget | 30 seconds | 10 minutes |
| Tool permissions | read only | read and write and send |
| Approval | every action | none |
| Verification | a human reads it | automatic checks |

A "fully autonomous agent" is just all of these turned up. You can turn them independently, and you should. A very common and very sensible setup is: unlimited read steps, approval required for anything that changes something.

**The shape of an autonomous run**

```
goal
  -> loop (with budgets checked every step)
  -> termination (one of three kinds)
  -> verification (separate, outside the agent)
  -> report (what actually happened, from evidence)
```

**Three kinds of termination**, and you need all three:

- **Success** — the model answers without asking for a tool. This is a *claim*, not a fact.
- **Budget** — steps, tokens or time ran out. Reliable, because it is your code.
- **Safety** — a loop was detected, or a tool failed repeatedly. Also your code.

Only two of those three are trustworthy. Notice which.

**Verification, and why it is separate**

The agent's final message is generated by the same process that generates everything else: what text is likely to come next. "I have completed the task" is an extremely likely thing to come next after a lot of work-looking activity, whether or not the work succeeded.

So verification has to look at evidence:

- **In code, where possible.** Did the file appear? Is it non-empty? Does it contain the date? This is the best kind, because it cannot be talked into anything.
- **With a second model call, where not.** Give a fresh model the original goal and the trajectory, and ask: was this achieved? Fresh matters — the agent that did the work is the worst judge of it.

**Blast radius**

Before turning autonomy up, ask: what is the worst thing this can do? An agent with `save_note` can write files in one folder. An agent with a delete tool, or an email tool, or a shell tool, has a much larger radius. The rails you need scale with the radius, not with the task.

### Stage 1 — Budgets

Start `autonomous.py` with the thing that stops runaway costs:

```python
import os, json, time, uuid
from datetime import datetime
from dotenv import load_dotenv
from openai import OpenAI, RateLimitError
from tools import TOOL_SCHEMAS, AVAILABLE_TOOLS

load_dotenv()
client = OpenAI(api_key=os.environ["GROQ_API_KEY"],
                base_url="https://api.groq.com/openai/v1")
MODEL = "llama-3.3-70b-versatile"


class Budget:
    def __init__(self, max_steps=25, max_tokens=40000, max_seconds=180):
        self.max_steps = max_steps
        self.max_tokens = max_tokens
        self.max_seconds = max_seconds
        self.steps = 0
        self.tokens = 0
        self.started = time.time()

    def spend(self, step_tokens):
        self.steps += 1
        self.tokens += step_tokens

    def exceeded(self):
        if self.steps >= self.max_steps:
            return f"step limit reached ({self.max_steps})"
        if self.tokens >= self.max_tokens:
            return f"token limit reached ({self.tokens})"
        if time.time() - self.started > self.max_seconds:
            return f"time limit reached ({self.max_seconds}s)"
        return None

    def summary(self):
        return (f"{self.steps} steps, {self.tokens} tokens, "
                f"{time.time() - self.started:.0f}s")
```

**Why three budgets and not one.**

Steps alone are not enough — one step that retrieves twenty chunks can cost more than five small ones.

Tokens alone are not enough — a tool that hangs uses no tokens at all while your program sits there forever.

**The time budget is the one people forget, and it is the one that saves you.** Any tool that waits on a network is a potential infinite hang. Steps and tokens both stay frozen while that happens. Wall-clock time is the only budget that notices.

### Stage 2 — Permission tiers

Not all tools are equally dangerous. Sort them:

```python
READ_ONLY = {"get_current_time", "calculate", "search_documents"}
WRITES    = {"save_note"}

POLICY = "ask"      # "ask" | "auto" | "dry_run"


def permitted(name, args):
    """Returns (allowed, message). Message is sent to the model when refused."""
    if name in READ_ONLY:
        return True, None

    if name not in WRITES:
        return False, f"The tool '{name}' is not permitted in this run."

    if POLICY == "auto":
        return True, None

    if POLICY == "dry_run":
        return False, f"DRY RUN: {name} was not actually executed. Assume it would have succeeded."

    print(f"\n  >>> agent wants to run {name}({args})")
    if input("  >>> allow? (y/n): ").strip().lower() == "y":
        return True, None
    return False, "The user refused permission for this action."
```

**Three things worth noticing.**

Unknown tools are refused by default, not allowed. If the model hallucinates a tool name, it gets a clear refusal rather than a `KeyError`.

Every refusal returns a **message for the model**, not an exception. The agent learns it was blocked and can adapt — "I couldn't save the file, here is the summary instead" — rather than dying.

**`dry_run` is the mode to use while developing.** The agent runs its whole trajectory, every write tool reports fake success, and nothing is actually changed. You get to watch what it *would* have done before letting it do it. Use this every time you give an agent a new tool.

### Stage 3 — The run, and a real result object

Day 7 returned a string. That is not enough when nobody was watching.

```python
def call_model(messages, tools, tries=4):
    for attempt in range(tries):
        try:
            return client.chat.completions.create(
                model=MODEL, messages=messages, tools=tools)
        except RateLimitError:
            wait = 2 ** attempt
            time.sleep(wait)
    raise RuntimeError("Rate limited repeatedly.")


AUTONOMOUS_PROMPT = """You are working on a task without a human watching.

HOW TO WORK
- Work in small steps. Say in one short sentence what you are doing and why.
- After each result, say what you learned and what is still missing.
- When everything is genuinely done, reply with a final answer and no tool calls.

RULES
- Never say you have done something unless a tool returned success for it.
- If a tool fails twice, stop and report the problem. Do not keep retrying.
- If you cannot complete the task, say exactly what you could and could not do.
- If you are blocked, stop and explain. Do not invent a result."""


def run(goal, budget=None, policy="ask"):
    global POLICY
    POLICY = policy
    budget = budget or Budget()

    run_id = datetime.now().strftime("%Y%m%d-%H%M%S") + "-" + uuid.uuid4().hex[:4]
    messages = [
        {"role": "system", "content": AUTONOMOUS_PROMPT},
        {"role": "user", "content": goal},
    ]
    trajectory = []
    seen_calls = []

    result = {"run_id": run_id, "goal": goal, "status": None,
              "answer": None, "reason": None, "trajectory": trajectory}

    while True:
        stop = budget.exceeded()
        if stop:
            result["status"] = "budget_exhausted"
            result["reason"] = stop
            break

        response = call_model(messages, TOOL_SCHEMAS)
        budget.spend(response.usage.total_tokens)
        message = response.choices[0].message

        if message.content:
            print(f"[{budget.steps}] {message.content[:150]}")

        if not message.tool_calls:
            result["status"] = "claimed_complete"
            result["answer"] = message.content
            break

        messages.append(message.model_dump(exclude_none=True))

        for call in message.tool_calls:
            name = call.function.name
            try:
                args = json.loads(call.function.arguments)
            except json.JSONDecodeError:
                args = {}

            signature = f"{name}:{json.dumps(args, sort_keys=True)}"
            if seen_calls.count(signature) >= 2:
                output = ("You have already tried this exact call twice without "
                          "progress. Try a different approach or stop and report.")
                trajectory.append({"tool": name, "args": args, "blocked": "loop"})
            else:
                seen_calls.append(signature)
                allowed, refusal = permitted(name, args)

                if not allowed:
                    output = refusal
                    trajectory.append({"tool": name, "args": args, "blocked": refusal})
                else:
                    try:
                        output = str(AVAILABLE_TOOLS[name](**args))
                        trajectory.append({"tool": name, "args": args,
                                           "result": output[:500], "ok": True})
                    except Exception as error:
                        output = f"Tool failed: {error}"
                        trajectory.append({"tool": name, "args": args,
                                           "result": output, "ok": False})

            print(f"   {name}({args}) -> {output[:100]}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": output})

    result["budget"] = budget.summary()

    with open(f"runs/{run_id}.json", "w") as f:
        json.dump(result, f, indent=2)

    return result
```

**The status field is the point of this stage.** Notice it says `claimed_complete`, not `complete`. The agent stopping asking for tools means it *thinks* it is done. Naming it honestly in your own code keeps you from forgetting that.

**Every tool call is recorded in `trajectory`**, including blocked and failed ones, and the whole thing is written to `runs/`. When an unsupervised run goes wrong at 2am, this file is the only thing you have.

### Stage 4 — Verify it, outside the agent

This is the most important stage of the day.

```python
VERIFIER_PROMPT = """You check whether a task was actually completed.

You will get the original goal and a record of everything the agent did.
Judge only by tool results. Ignore anything the agent said about itself.

Reply with JSON only:
{"verdict": "done" | "partial" | "failed",
 "evidence": "the specific tool result that proves it, or what is missing",
 "confidence": "high" | "low"}"""


def verify_with_model(result):
    record = json.dumps(result["trajectory"], indent=2)[:6000]

    response = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": VERIFIER_PROMPT},
            {"role": "user", "content": f"GOAL:\n{result['goal']}\n\nWHAT THE AGENT DID:\n{record}"}
        ],
        temperature=0,
        response_format={"type": "json_object"}
    )
    return json.loads(response.choices[0].message.content)


def verify_in_code(expected_file=None, must_contain=None):
    """The kind of check that cannot be argued with."""
    if not expected_file:
        return None
    if not os.path.exists(expected_file):
        return {"verdict": "failed", "evidence": f"{expected_file} does not exist"}
    text = open(expected_file).read()
    if len(text.strip()) < 20:
        return {"verdict": "failed", "evidence": f"{expected_file} is nearly empty"}
    if must_contain and must_contain.lower() not in text.lower():
        return {"verdict": "partial", "evidence": f"'{must_contain}' not found in the file"}
    return {"verdict": "done", "evidence": f"{expected_file} exists, {len(text)} characters"}
```

Use both:

```python
if __name__ == "__main__":
    result = run(
        "Search my documents for anything about deadlines. Save a note called "
        "'deadlines' listing each one with its source filename.",
        budget=Budget(max_steps=20, max_tokens=40000, max_seconds=180),
        policy="auto"
    )

    print("\n--- agent says ---")
    print(result["status"], "|", result["budget"])
    print(result["answer"])

    print("\n--- code check ---")
    print(verify_in_code("notes/deadlines.txt", must_contain="deadline"))

    print("\n--- model check ---")
    print(verify_with_model(result))
```

**Why the verifier gets the trajectory and not the answer.** Hand it the agent's summary and you are asking one model to grade another model's essay about itself. Hand it the tool results and it is checking evidence. `"Judge only by tool results. Ignore anything the agent said about itself"` is the line doing the work.

**`verify_in_code` is worth more than `verify_with_model`.** It cannot be persuaded. Whenever a goal has a checkable outcome — a file, a row in a database, a value that should have changed — check it in code. Use the model verifier only for things code cannot judge, like whether a summary is actually about deadlines.

### Stage 5 — Make it notice it is stuck

Loop detection catches identical repeats. It misses the more common failure: slow drift, where it keeps doing slightly different things and getting nowhere.

Add a nudge every few steps:

```python
CHECK_EVERY = 5

        if budget.steps > 0 and budget.steps % CHECK_EVERY == 0:
            messages.append({
                "role": "user",
                "content": ("Pause. In two sentences: what have you actually completed "
                            "so far, and what is left? If you are not making progress, "
                            "stop now and report what you achieved.")
            })
```

Run a hard task and watch what it says at step 5, 10, 15.

**This works better than it has any right to.** Being asked to state progress forces the model to read its own trajectory and compare it against the goal — and models are considerably better at spotting a stall when asked directly than at noticing one while in the middle of it.

It costs one extra call every five steps. Cheap, for the number of runaway runs it ends early.

## 7. Words I heard today

| Word | Plain meaning |
|---|---|
| **Autonomy** | How much the agent does without asking. A set of dials. |
| **Budget** | A hard limit on steps, tokens or time. |
| **Termination condition** | Any rule that ends the run. |
| **Trajectory** | The full record: every call, argument and result. |
| **Verification** | Checking the goal was met, from evidence, outside the agent. |
| **Self-report** | The agent's own claim about what it did. Not evidence. |
| **Guardrail** | Any rule limiting what the agent may do. |
| **Blast radius** | The worst damage this agent could cause. |
| **Dry run** | Executing the trajectory with write tools faking success. |
| **Idempotent** | Safe to run twice. Matters a lot when retries exist. |
| **Circuit breaker** | Stopping after repeated failures instead of retrying forever. |
| **Audit log** | The saved record of what happened. Your `runs/` folder. |
| **Human in the loop** | A person approving actions. |

## 8. Break it on purpose

**1. Measure how often it lies.**
Run five different tasks with `policy="auto"`. For each, record what the agent claimed and what `verify_in_code` found. Count the disagreements.
*You will see:* a real number, on your machine, for how often "done" is not done.
*It teaches:* this is the most valuable experiment in the course. Everyone is told not to trust self-reports. Very few people measure it.

**2. Hang a tool.**
Put `time.sleep(600)` inside `get_current_time`. Run with a step and token budget but comment out the time check.
*You will see:* nothing, for ten minutes. Steps and tokens never move.
*It teaches:* why the time budget exists. It is the only one that catches this.

**3. Starve it.**
Set `max_tokens=8000` on a task needing twenty steps.
*You will see:* `budget_exhausted` with half the work done — maybe a file created and left empty.
*It teaches:* partial completion is the dangerous state. Neither done nor undone, and no rollback.

**4. Remove the "never claim" rule.**
Take that line out of `AUTONOMOUS_PROMPT`, then break `save_note` so it returns an error. Run a save task.
*You will see:* a cheerful report of success.
*It teaches:* prompt rules genuinely help — and are genuinely not enough, which is why Stage 4 exists.

**5. Hallucinate a tool.**
Add to the goal: "use the send_email tool to email me the results."
*You will see:* it tries to call a tool that does not exist, gets your refusal message, and adapts.
*It teaches:* deny by default turns a crash into a conversation.

**6. Break the verifier on purpose.**
Feed `verify_with_model` a trajectory where nothing worked, but hand it the agent's glowing summary instead of the tool results.
*You will see:* it often agrees the task was done.
*It teaches:* the verifier is only as good as what you show it. Evidence in, judgement out.

## 9. Traps

**Trap 1 — believing `claimed_complete`**
*Symptom:* your pipeline reports success and produces nothing.
*Fix:* never treat the agent's stopping as success. Verify in code where you can.

**Trap 2 — no time budget**
*Symptom:* a program that never returns and shows no activity.
*Fix:* wall-clock budget, checked every step.

**Trap 3 — tools that are not safe to repeat**
*Symptom:* three identical notes, or the same message sent three times.
*Cause:* a retry after a timeout, where the first call actually succeeded.
*Fix:* make write tools idempotent — same input, same result, no duplicate. A stable id or filename is usually enough.

**Trap 4 — no audit log**
*Symptom:* "it did something wrong last night" and nothing to look at.
*Fix:* write the trajectory to `runs/` on every run, including failed ones. Especially failed ones.

**Trap 5 — blast radius bigger than the rails**
*Symptom:* fine for weeks, then something irreversible.
*Cause:* a powerful tool added to an agent whose guardrails were designed for a weaker one.
*Fix:* every time you add a tool, ask what the worst case is now, and re-check the rails. Adding a tool is a security change.

**Trap 6 — autonomy where it was not needed**
*Symptom:* a thirty-step agent run for something one API call answers.
*Fix:* ask whether the task actually needs multiple steps. Most do not. Day 15 covers choosing.

## Answers

**1.** Budget termination and safety termination, because both are enforced by your own code. Success termination cannot be trusted, because it only means the model stopped asking for tools — a claim produced by the same process that produces everything else it says.

**2.** A hanging tool consumes no steps and no tokens. Both those budgets stay frozen while your program waits forever. Wall-clock time is the only measure that keeps moving.

**3.** Because the final answer is the agent's own account of itself, and asking a model to grade that is asking it to grade an essay about the thing rather than the thing. The trajectory contains actual tool results, which is evidence.

**4.** A run where the agent does everything normally but write tools report fake success without changing anything. Use it every single time you give an agent a new tool that can change something, before letting it run for real.

**5.** Non-idempotent tools. The fix is to make write operations safe to repeat — a stable id or filename so the same call produces the same single outcome instead of a duplicate.
