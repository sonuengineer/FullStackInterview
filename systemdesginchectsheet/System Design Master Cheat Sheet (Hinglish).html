System Design Master Cheat Sheet

Senior / Lead Full-Stack & Backend interview revision, Hinglish mein. Pehle common-sense analogy, phir technical explanation, phir production reality aur interview points.

Goal: Ye document padhne ke baad koi bhi production architecture dekh ke tum bata sako ki har major component kyun hai, kya problem solve karta hai, aur fail ho jaye to kya hoga.

1Complete production architecture

Ek real production app (jaise tumhara React + Node.js product) me request seedhe "server" tak nahi jaati. Beech me kai layers hoti hain, aur har layer ek specific problem solve karti hai.

Request journey: Browser → Response

  1. Browser me user myapp.com/dashboard type karta hai. Browser ko IP chahiye, naam se network nahi chalta.
  2. DNS lookup hota hai (browser cache → OS cache → resolver → root → TLD → authoritative). Result: CloudFront ya ALB ka address.
  3. Browser us address se TCP + TLS (HTTPS) connection banata hai.
  4. CDN edge request receive karta hai. Static file (JS/CSS/image) cached hai to HIT aur turant response. Nahi hai to MISS, origin se laata hai, cache karta hai.
  5. Dynamic API request (/api/orders) CDN se origin ki taraf jaati hai, yaani Load Balancer ke paas.
  6. LB healthy servers me se ek choose karta hai (round robin / least connections).
  7. Backend (Node.js) request process karta hai: auth verify (JWT/session), validation, business logic.
  8. Backend pehle Redis check karta hai. HIT = data mil gaya. MISS = aage jao.
  9. Redis miss pe Database query (reads replica se, writes primary pe). Result Redis me SET hota hai (TTL ke saath).
  10. Response wapas: Backend → LB → (CDN) → Browser. Browser React UI render karta hai.
Remember this

Har layer ka ek hi kaam hai: request ko origin database tak pahunchne se pehle jitna ho sake rok lo ya halka kar do. DNS naam resolve karta hai, CDN cache se answer deta hai, LB traffic baantta hai, Redis DB ka load kam karta hai. Database sabse expensive aur scale karne me sabse mushkil hai, isliye use last me rakha jaata hai.

Har component ka breakdown

DNS / Route53

What it does
Domain name ko IP address (ya CDN/LB ke address) me convert karta hai.
Why we need it
Log myapp.com yaad rakhte hain, machines IP se baat karti hain. Phone ki contact list jaisa.
Problem solved
Server ka IP badle to users ko kuch pata nahi chalta, sirf DNS record update hota hai. Route53 health check se traffic ko healthy region me bhi bhej sakta hai.
If it fails
Naye users site khol hi nahi paate (site "down" dikhti hai) chahe servers bilkul theek hon. Already-cached DNS wale users kuch der chalte rehte hain. Isliye managed DNS (multi-AZ, anycast) use karte hain.
Production example
Route53 Alias record app.myapp.com → CloudFront distribution, aur api.myapp.com → ALB.
Interview point
"TTL kitna rakhoge?" Migration se pehle TTL kam karo (60s), migration ke baad wapas badhao.

CDN / CloudFront

What it does
Duniya bhar ke edge locations pe content ki copy rakhta hai aur user ke sabse paas wale edge se serve karta hai.
Why we need it
Mumbai ke user ko Virginia ke server tak har baar jaana pade to latency badhti hai. Edge paas hota hai.
Problem solved
High latency, origin pe heavy load, DDoS absorption, bandwidth cost.
If it fails
CloudFront itself bahut resilient hai, lekin agar edge me issue ho to traffic origin pe seedha aa sakta hai (origin overload risk). Multi-CDN ya DNS failover advanced setups me hota hai.
Production example
React build (JS/CSS/images) S3 + CloudFront se serve hoti hai, hashed filenames (main.a91f3.js) ke saath long TTL.
Interview point
Cache invalidation: hashed filenames > manual invalidation.

Load Balancer (ALB / Nginx)

What it does
Incoming traffic ko multiple healthy servers me distribute karta hai. TLS termination aur health check bhi karta hai.
Why we need it
Ek server ki limit hoti hai. Bahut users aayenge to ek server dher ho jayega.
Problem solved
Single point of failure hatata hai, horizontal scaling possible banata hai, zero-downtime deploys.
If it fails
Poori app unreachable. Isliye ALB managed hai (multi-AZ, khud redundant). Self-managed Nginx ho to 2+ instances + floating IP / DNS failover.
Production example
ALB path routing: /api/* → Node target group, /admin/* → admin service.
Interview point
"LB khud SPOF kaise nahi banta?" Managed multi-AZ ya active-passive pair.

EC2 App Servers + Auto Scaling

What it does
Tumhara Node.js code chalate hain. Auto Scaling load ke hisaab se servers ki count badhata/ghatata hai.
Why we need it
Traffic constant nahi hota (sale, viral post, subah/shaam). Fixed servers ya to waste hote hain ya crash.
Problem solved
Capacity vs cost balance, aur unhealthy instance ka auto-replacement.
If it fails
Ek EC2 mara to LB health check use nikal deta hai, ASG naya bana deta hai. Users ko (ideally) fark nahi padta, agar app stateless hai.
Production example
Min 2 (alag AZ me), desired 3, max 10; CPU 60% target tracking.
Interview point
Servers cattle hain, pets nahi: replaceable.

Redis

What it does
In-memory key-value store, sub-millisecond reads. Cache, session, rate limit, lock, counter.
Why we need it
DB disk-based hai aur expensive. Repeated reads baar baar DB pe kyun bhejein?
Problem solved
DB load, slow reads, shared state across servers.
If it fails
Cache miss storm: sab requests DB pe. Agar Redis me sessions the to users logout. Isliye replica/cluster + DB protection (see section 8, 18).
Production example
ElastiCache Redis (primary + replica, multi-AZ) for product-catalog cache aur rate limiting.
Interview point
Redis source of truth nahi hai (usually). DB hai.

Database (Primary + Read Replicas)

What it does
Durable business data store karta hai (orders, users, payments). Primary writes leta hai; replicas reads serve karte hain.
Why we need it
Server/Redis restart pe data nahi jaana chahiye. Durability + consistency + queries.
Problem solved
Data persistence, ACID transactions, read scalability via replicas.
If it fails
Primary down = writes band. Managed DB (RDS Multi-AZ / Aurora) automatic failover karta hai (tens of seconds se ~2 min). Replica down = reads doosre replica pe.
Production example
RDS PostgreSQL Multi-AZ + 2 read replicas; reports/analytics replica pe.
Interview point
"Sabse pehle bottleneck kaun banta hai?" Aksar DB.
Interview tip

Jab bhi architecture draw karo, request ki journey left to right bolte hue draw karo aur har box ke baad ek line bolo: "Ye ye problem solve karta hai, aur fail hone pe ye hoga." Ye Senior/Lead level ka signal hai.

Common mistake

Pehle hi din "microservices + Kafka + sharding + Kubernetes" bol dena. Interviewer ko dikhana hai ki tum zaroorat ke hisaab se complexity add karte ho: pehle single server + DB, phir cache, phir LB, phir replicas, aur sharding sabse last.

  • DNS-based load balancing / failover kaise hota hai? (Route53 weighted/latency/failover routing + health checks.)

3CDN

Analogy

Ek famous bakery sirf Delhi me hai (origin). Mumbai ke log biscuit mangayein to har baar Delhi se aana padega: slow. Isliye bakery har sheher me local shops (edge) me biscuit ka stock rakhti hai. Stock hai to turant (HIT), nahi hai to Delhi se mangao (MISS), rakh lo, agle customer ko turant do.

TermMeaning
Origin serverAsli content ka source: S3 bucket, ALB, tumhara Node server.
Edge serverUser ke paas wala CDN server jo cache rakhta hai.
Cache HITEdge ke paas content hai, turant serve. Origin ko pata bhi nahi chalta.
Cache MISSEdge ke paas nahi hai, origin se laata, cache karta, phir serve karta.
TTLEdge kitni der content ko fresh maane. Uske baad revalidate/refetch.
Static contentSabke liye same: JS, CSS, images, fonts, video. CDN ke liye ideal.
Dynamic contentUser-specific ya real-time: /api/me, cart. Normally cache nahi (ya bahut short TTL / careful cache key).
 HIT :   User ──► CloudFront Edge ──► (cache me hai) ──► Response to User        ~10-30 ms

 MISS:   User ──► CloudFront Edge ──► (cache me nahi)
                                          │
                                          ▼
                                       Origin (S3 / ALB)
                                          │
                                          ▼
                              Edge me CACHE hota hai ──► Response to User
                              (agla user isi edge se HIT paayega)

CDN aur latency / origin load

  • Latency: Physical distance kam, network hops kam. Speed of light ko hum badal nahi sakte, sirf content paas la sakte hain.
  • Origin load: 1 million users ek hi image maangein to origin ko sirf ek-do baar hit hota hai, baaki edge se. Cache hit ratio (90%+) ek key metric hai.

Remember this

Tum har file manually CDN pe upload nahi karte. CDN pull-through cache hai: pehli request pe origin se khud le aata hai. Tum sirf origin me deploy karte ho (S3 / Vercel build), aur CDN khud cache bharta hai. Naye release me content-hashed filenames use karo (app.7c3f1.js) taaki invalidation ki zaroorat hi na pade; sirf index.html ka TTL chhota rakho.

DNS ne bataya ki CloudFront edge kahan hai. CDN cache ne wahan se content diya. Dono alag layers hain.

Production example

Bug fix deploy hua par users ko purani JS mil rahi hai: index.html ko long TTL de diya tha. Fix: HTML pe Cache-Control: no-cache ya short TTL, assets pe max-age=31536000, immutable (hashed names).

Interview questions
  • Dynamic API responses CDN pe cache kar sakte ho? Kab? (Public, user-independent data, short TTL, correct cache key.)
  • CDN cache poison ya private data leak kaise hota hai? (Cache key me Authorization/cookie ignore ho jaye to.)
  • Cache invalidation kaise? (Versioned URLs > invalidation API.)

4Load Balancer

Analogy

Traffic police chowk pe khada hai. Gaadiyan (requests) aati hain, wo dekhta hai kaunsi lane khaali hai aur wahan bhej deta hai. Jo lane band hai (accident = unhealthy server) wahan gaadi nahi bhejta.

 Users ──► Load Balancer ─┬─► Server 1
                          ├─► Server 2
                          └─► Server 3      (Server 3 unhealthy ho to LB use skip karega)
Load Balancer = decide karta hai KIS server ko traffic milega.
ConceptMeaningProduction note
ALBAWS Application LB, Layer 7 (HTTP/HTTPS). Path/host based routing, WebSocket, HTTP/2.Web apps/APIs ke liye default choice. (NLB = Layer 4, TCP, ultra low latency.)
NginxSoftware reverse proxy/LB, khud configure aur manage karte ho.Kubernetes ingress, on-prem, ya EC2 ke andar reverse proxy.
Health checkLB periodically GET /health maarta hai. Fail hua to server rotation se bahar.Health endpoint shallow rakho (app up hai?). Deep checks (DB down) se poore servers ek saath nikal sakte hain.

Least ConnectionsJis server pe sabse kam active connections, use do.Requests ka duration alag-alag ho (long uploads, websockets) to better.

HTTP request ≠ TCP connection

Beginners sochte hain "1 request = 1 connection". Aisa nahi hai.

  • HTTP/1.1: Keep-alive se ek TCP connection pe kai requests sequentially.
  • HTTP/2: Ek TCP connection pe multiplexing: kai requests parallel streams me.
  • HTTP/3: TCP ki jagah QUIC (UDP) pe; connection migration aur kam head-of-line blocking.
Remember this

Ek client ka ek long-lived connection ek hi server se chipka reh sakta hai. Isliye "round robin" me load kabhi-kabhi uneven dikhta hai: LB connection ya request level pe balance kar raha hai, ye check karo. ALB L7 hai, HTTP request level pe route kar sakta hai; NLB connection level pe.

Conceptual Round Robin (sirf samajhne ke liye)

// Concept demo: production me ye khud MAT likho
const servers = ["http://s1:3000", "http://s2:3000", "http://s3:3000"];
let i = 0;

function nextServer() {
  const s = servers[i];
  i = (i + 1) % servers.length; // 0 → 1 → 2 → 0 ...
  return s;
}

// Har request pe: proxy(req, nextServer())
Common mistake

Interview me "Node.js me apna load balancer bana lunga". Production me ALB / Nginx / HAProxy / Envoy use hote hain: health checks, TLS, connection draining, retries, observability, aur battle-tested performance ke saath. Custom Node LB khud ek SPOF aur maintenance bojh ban jaata hai. (Upar ka code sirf algorithm samjhane ke liye hai.)

Interview questions
  • L4 vs L7 load balancer?
  • Health check fail hone pe kya hota hai? Draining kya hai?
  • Load balancer khud fail ho jaye to? (Multi-AZ managed / redundant pair.)

Remember this: ephemeral servers

Production me app servers replaceable / ephemeral hone chahiye: kabhi bhi mar sakte hain, naye ban sakte hain. Isliye: server pe manually SSH karke code mat daalo, local disk pe important data mat rakho, config environment/Secrets Manager se lo, aur har deploy ek naya immutable image ho. Isse scale, rollback, aur recovery sab predictable ho jaata hai.

Common mistakes
  • Auto scaling lagaya par app stateful hai (sessions RAM me, uploads local disk pe). Naya server aaya to kaam ka nahi.
  • Sirf app scale kiya, DB nahi. 10 servers × 20 connections = 200 DB connections; DB ne jawab de diya.
  • Slow startup: instance ready hone me 5 min lagte hain, tab tak spike nikal gaya. Pre-baked AMI/image, warm pool ya scheduled scaling use karo.
  • Scale-in pe requests kaat di gayi: connection draining na ho.
Interview questions
  • CPU vs request-count vs queue-based scaling kab?
  • Scale out fast hota hai par scale in slow kyun rakhte hain? (Flapping se bachne ke liye cooldown.)
  • Deploy strategy: rolling, blue/green, canary me kya farak?

Problem: session server ki RAM me

 Login request:

Analogy

Ek bank branch me clerk ne tumhari details apne dimaag me rakhi. Agli baar doosre clerk ke paas gaye to usse kuch pata nahi. Fix: details shared register (Redis/DB) me rakho jo sab clerks dekh sakte hain.

                        ├─► Server #2 ─┼──► Redis (sessions)   ✔ kisi bhi server pe chalega
                        └─► Server #3 ─┘
TermMeaningTrade-off
Stateful backendServer khud user ki state (session, cart) memory/disk me rakhta hai.Scale aur failover mushkil; server marne pe state gayab.
Stateless backendHar request me sab zaroori info aati hai ya shared store se li jaati hai; server kuch yaad nahi rakhta.Kisi bhi server pe request chal jaati hai; scaling easy.
Sticky sessions / Session affinityLB ek user ko hamesha same server pe bhejta hai (cookie se).Quick fix; par uneven load, server mara to session gaya, scale-in painful.

Remember this

"Stateless" ka matlab ye nahi ki app me koi state nahi. Matlab: state app server ke bahar hai (Redis, DB, S3, token me). Isse server disposable ho jaata hai.

Common mistake

File uploads /uploads local folder me save karna, in-memory rate-limit counters, in-memory cache jo servers ke beech consistent nahi. Ye sab bhi hidden state hain. Multi-instance me alag-alag behaviour aayega.

Interview question

"Sticky sessions kab theek hain?" Legacy app migration ke temporary step, ya WebSocket connection affinity. Long-term me shared session store better.

7JWT + Cookies

Cookie ≠ JWT. Cookie = storage / transport mechanism. JWT = token format.
Analogy

JWT ek signed ID card hai jisme tumhara naam aur role likha hai aur uspe issuer ki mohar (signature) hai. Cookie wo pocket/wallet hai jisme browser wo card rakhta hai aur har request ke saath dikhata hai. Card koi bhi pocket me ho sakta hai (Authorization header, cookie, memory).

JWT ke 3 parts

 xxxxx.yyyyy.zzzzz
   │      │      └─ Signature : HMAC/RSA(header + payload, secret/private key)  → tamper detect
   │      └──────── Payload   : claims {"sub":"u42","role":"admin","exp":1735689600}
   └─────────────── Header    : {"alg":"RS256","typ":"JWT"}
Common mistake: JWT signed hota hai, encrypted nahi

Payload sirf base64url encoded hai, koi bhi decode karke padh sakta hai. Isliye password, secrets, card numbers, sensitive PII JWT me kabhi mat daalo. Signature sirf ye batata hai ki data badla nahi gaya, ye nahi ki wo chhipa hua hai.

TermMeaning

async function getUser(id) {
  const key = `user:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);          // HIT

  const user = await db.query("SELECT * FROM users WHERE id=$1", [id]); // MISS
  if (user) await redis.set(key, JSON.stringify(user), "EX", 300);       // TTL 5 min
  return user;
}

async function updateUser(id, data) {
  await db.query("UPDATE users SET ... WHERE id=$1", [id]);
  await redis.del(`user:${id}`);                  // invalidate on write
}

10Database connection pool

Analogy

Restaurant me tables (connections) limited hain. Har customer ke liye naya table banake, khaane ke baad tod dena bekaar hai. Pehle se 10 tables laga do, customers aate hain, baithte hain, uthte hain, table dobara use hota hai. Table khaali nahi to customer wait karta hai (queue).

 Without pool:   Request ─► DB connection banao (TCP + TLS + auth) ─► Query ─► Connection band
                            ▲ har request pe 10-100 ms extra + DB pe load

 With pool:      Application ─► Connection Pool ─► pehle se khula connection ─► DB
                                 (borrow → query → release wapas pool me)

DB connection expensive kyun: TCP handshake, TLS, authentication, aur PostgreSQL me har connection ek alag process (kai MB memory). Bahut connections = DB memory/CPU context-switching me doob jaata hai.

Node.js practical example (node-postgres)

import { Pool } from "pg";

// App start pe EK BAAR banao, har request pe nahi
export const pool = new Pool({
  host: process.env.DB_HOST,
  max: 10,                        // max connections per instance
  idleTimeoutMillis: 30_000,      // idle 30s baad close
  connectionTimeoutMillis: 2_000, // pool se connection ka wait limit
});

// Simple query: pool khud borrow + release karta hai
const { rows } = await pool.query("SELECT * FROM orders WHERE user_id=$1", [uid]);

// Transaction: ek hi connection chahiye, isliye manual borrow
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("UPDATE accounts SET bal = bal - $1 WHERE id=$2", [amt, from]);
  await client.query("UPDATE accounts SET bal = bal + $1 WHERE id=$2", [amt, to]);
  await client.query("COMMIT");
} catch (e) {
  await client.query("ROLLBACK");
  throw e;
} finally {
  client.release();               // MUST: warna connection leak
}
Common mistakes
  • client.release() finally me na karna: leak.
  • Har request me naya new Pool() ya new Client() banana.
  • Auto scaling ke saath pool size fix rakhna: 50 instances × 20 = 1000 connections, DB down. Fix: chhota pool per instance, ya PgBouncer / RDS Proxy.
  • Serverless (Lambda) me har invocation nayi connection: proxy zaroori.
Interview question

"Pool bada karne se performance hamesha badhti hai?" Nahi. DB ke CPU cores ke hisaab se ek limit ke baad throughput girta hai. Chhota, sahi-sized pool aksar behtar hota hai.

11Database replication

 Application ──write──► PRIMARY ──replication──► Replica 1 ──► reads

  • Replication: primary apne changes ka log (WAL / binlog) replicas ko bhejta hai; replicas usse apply karte hain.
  • Read from replicas: SELECT ko replicas pe bhejo; primary ka load kam.
  • Failover: primary mara to ek replica ko promote karke naya primary banate hain (managed DB automatic karta hai). Is dauraan kuch seconds/minutes writes fail ho sakte hain.

Multiple servers hain to counter shared hona chahiye, isliye Redis. Server RAM me counter rakhoge to har server ki apni limit ban jaayegi (10 servers = 10x limit).

// 100 requests / minute / user  (fixed window)
async function rateLimit(req, res, next) {
  const key = `rl:${req.user.id}:${Math.floor(Date.now() / 60000)}`;

  const count = await redis.incr(key);        // atomic
  if (count === 1) await redis.expire(key, 60);

  if (count > 100) {
    res.set("Retry-After", "30");
    return res.status(429).json({ error: "Too many requests" });
  }
  next();
}
// Production: INCR + EXPIRE ko Lua script me atomic banao (ya library use karo).

  • Different limits: per user, per IP, per API key, per endpoint (login pe strict, GET pe relaxed).
  • Redis down ho to fail-open (availability) ya fail-closed (security): login/OTP jaise sensitive endpoints ke liye soch-samajh ke decide karo.
Common mistake

16HTTPS / TLS

Analogy

HTTP = postcard: raaste me har koi padh sakta hai. HTTPS = sealed, tamper-proof courier box, jise sirf receiver kholta hai, aur courier ka ID bhi verified hota hai (ki sahi bank hai, nakli nahi).

TermMeaning
TLSTransport Layer Security. HTTPS = HTTP over TLS. (SSL purana naam/protocol hai.)

Handshake (simplified, TLS 1.3)

  2. Server: cipher chunta hai, apna key-exchange share aur certificate bhejta hai.
  3. Browser certificate verify karta hai: trusted CA ne sign kiya? domain match? expired to nahi?

Production

Common mistake

Certificate expire hone dena (sabse common outage!). Auto-renewal + expiry alerts lagao. Aur "HTTPS lagaya to security done" nahi: XSS, SQL injection, weak auth alag issues hain.

Interview question

"HTTPS me man-in-the-middle kaise rokta hai?" Certificate authentication: attacker ke paas domain ka valid certificate/private key nahi hoga.

p50 / p95 / p99 (Hinglish me)

 p50 = 100 ms  →  50% requests 100 ms ya usse tez.         "Typical user ka experience"
 p95 = 300 ms  →  95% requests 300 ms ya usse tez.         "20 me se 1 user 300 ms se zyada wait karta hai"
 p99 = 800 ms  →  99% requests 800 ms ya usse tez.         "100 me se 1 user 800 ms+ wait karta hai (tail)"
Analogy

Office jaane me roz avg 30 min lagte hain (p50). Par 20 din me 1 din 1 ghanta lagta hai (p95), aur mahine me ek din 2 ghante (p99). Average kehta hai "sab theek", par wo ek din meeting miss karwa deta hai.

Remember this

Average (mean) chhupa deta hai. Slow tail ko p95/p99 dikhate hain. Ek page me 20 backend calls hon to user ko kam se kam ek p99-slow call milne ka chance high hota hai. Isliye SLO aksar p95/p99 pe likhe jaate hain, average pe nahi.

Monitoring, alerting, debugging, bottleneck detection

  • Monitoring: dashboards jo system ki health continuously dikhate hain (RED: Rate, Errors, Duration; USE: Utilization, Saturation, Errors).
  • Alerting: symptoms pe alert (error rate, p99, SLO burn), sirf causes (CPU 70%) pe nahi. Actionable ho, warna alert fatigue.
  • Debugging: alert → dashboard → trace (kahan slow) → logs (kyun) → fix → postmortem.
  • Bottleneck detection: jis resource ki utilization/saturation sabse pehle 100% ke paas jaaye (CPU, DB connections, disk IO, external API) wahi bottleneck.
Common mistake

Unstructured logs, requestId/traceId na hona, aur high-cardinality metrics (labels me userId) daal ke monitoring bill/performance bigaad dena. Logs me passwords/tokens/PII mat likho.

Interview question

"Monitoring aur observability me farak?" Monitoring = known problems ke liye pre-defined checks. Observability = unknown problems ko data (logs/metrics/traces) se explore kar pana.

Debugging steps (order)

  1. Scope pehchano: Sabhi users ya kuch? Sabhi endpoints ya ek? Kab se? Deploy hua tha? (Change correlation.)
  2. Percentiles dekho: p50 badha ya sirf p99? Sirf tail = specific slow path/query/dependency. Sabka badha = capacity/saturation.
  3. Trace kholo: Kaunsa span sabse lamba hai? Wahin drill down.
  4. Saturation check: CPU, DB connections, pool wait, queue depth, disk IO.
  5. Fix ka type: index/query fix, cache, timeout/circuit breaker, scale out, async via queue, payload compress.
  6. Verify aur prevent: metrics normal hue? Alert/SLO/load test add karo.
Remember this

Latency = ek request ko kitna time. Throughput = ek second me kitni requests. Load badhne par throughput ek limit pe flat hota hai aur latency achanak khadi ho jaati hai (queueing). Wo point saturation hai, wahi bottleneck hai.

Common mistakes
  • Bina measure kiye optimize karna ("Redis laga dete hain").
  • Sirf average latency dekhna.
  • Server scale out karna jab bottleneck DB ya external API hai (problem aur badhti hai).
  • Node me CPU-heavy kaam main thread pe (event loop block): worker threads/queue use karo.
Interview tip

Ye chain bolo: "Pehle main dekhunga ki slowness kahan hai: client, network, ya server. Phir trace se dominant span, phir us layer ki saturation aur logs." Ye structured approach hi answer hai.

22Mock interview

Interviewer

"Design a URL Shortener like Bitly. Assume: 10 million users, 100 million redirects/day. Design the complete production architecture."

Abhi answer nahi diya ja raha. Neeche interviewer ka evaluation sheet hai: interview me kya poochha jaayega aur kya expected hai. Pehle khud socho, phir answer do.

1. Requirements questions (tum interviewer se poochho)

  • Sirf shorten + redirect, ya custom alias, expiry, analytics, edit/delete bhi?
  • Short URL kitna chhota chahiye? Kaunse characters? Kya guess na kiya ja sake?
  • Kya same long URL ke liye same short URL milna chahiye?
  • Users authenticated hain? API access bhi?
  • Links kab expire hote hain? Kitne saal data rakhna hai?
  • Multi-region users? Latency target?

2. Scale questions

  • 100M redirects/day ka average aur peak QPS kya hoga? (Back-of-envelope: average ≈ 1,150/s; peak 5-10x.)
  • Read:write ratio kya hai? Naye URLs/day kitne? 5 saal me total URLs kitne?
  • Har record ka size kitna? Total storage?
  • Kitna traffic cacheable hai (popular links)? Hit ratio target?
  • Redirect latency ka SLO kya (p95/p99)?

3. Functional requirements (expected)

  • Long URL do → unique short URL milna.
  • Short URL kholo → original URL par redirect.
  • Optional: custom alias, expiry, click analytics, link disable.

4. Non-functional requirements (expected)

  • Redirect highly available aur low-latency (read path critical).
  • Short codes unique aur collision-free; predictable/enumerable nahi.
  • Durable storage (links kho nahi sakte).
  • Read-heavy system; horizontally scalable; abuse protection (spam/malware links, rate limiting).
  • Analytics eventual consistency me chalega, redirect path block nahi karna chahiye.

5. Expected architecture components

Interviewer ki checklist (pehle khud socho, phir kholo)
  • DNS + CDN/edge caching for popular redirects
  • Load balancer + stateless app servers with auto scaling
  • Redis cache for short code → long URL (cache-aside, TTL, LRU)
  • Database choice with reasoning (key-value/NoSQL vs SQL), primary + replicas, index on short code
  • Short code generation strategy (counter + base62, pre-generated key service/ranges, hashing + collision handling)
  • 301 vs 302 redirect trade-off (caching vs analytics)
  • Async click analytics via queue + workers (redirect path me sync write nahi)
  • Rate limiting, URL validation/abuse checks, expiry cleanup
  • Sharding/partitioning plan and when it is needed (with numbers)
  • Observability, failure handling (cache/DB/queue down), multi-AZ / multi-region

6. Follow-up questions

  • Do servers ek hi waqt same short code generate kar dein to collision kaise rokoge?
  • Redis down ho jaye aur saari redirects DB pe aa jaayein to?
  • Ek viral link pe achanak 1M requests/min aayein (hot key), to?
  • Analytics accurate rakhna hai par redirect latency nahi badhani: kaise?
  • Kab tak single DB chalega? Sharding kab aur kis key pe karoge?
  • Multi-region me ek link ka data kaise consistent rakhoge?
  • Malicious/phishing URLs kaise handle karoge?
Ab tumhari baari

Apna answer likho. Is order me chalo: (1) requirements clarify, (2) back-of-envelope numbers, (3) high-level architecture diagram, (4) short code generation + data model, (5) read/redirect path (CDN → LB → app → Redis → DB), (6) write path, (7) async analytics, (8) scaling aur failure handling, (9) trade-offs.

Jab ready ho, apna answer yahin chat me bhejo. Main interviewer ki tarah follow-up sawal poochhunga aur feedback dunga.

Final golden rules

  1. DNS finds where the service is.
  2. CDN brings content closer to users.
  3. Load Balancer distributes traffic.
  4. Auto Scaling changes server count.
  5. Stateless servers make scaling easier.
  6. Redis provides fast shared state/cache.
  7. Database stores durable business data.
  8. Replicas improve read scalability.
  9. Sharding distributes database data/workload.
  10. Object storage handles files.
  11. Queues move heavy work out of request paths.
  12. Workers perform background work.
  13. Rate limiting protects services.
  14. HTTPS protects data in transit.
  15. Observability tells us what is happening.
  16. p95/p99 expose slow-tail requests.
  17. Every production design should ask: "What happens when this component fails?"
